# 최적화 일지

최적화 작업마다 가설, 변경, 검증, 측정 결과와 다음 판단을 기록한다. 구현상 비용 감소와 측정으로 확인된 성능 개선을 구분하며, 실패하거나 개선이 관찰되지 않은 시도도 남긴다.

## 기록 규칙

- 날짜, 대상, 최적화 전후 커밋과 동일 측정 조건을 명시한다.
- 원본과 요약은 벤치마크 문서에 보존하고 이 일지에서 링크한다.
- 처리량과 지연 시간을 함께 비교하며, 워밍업 제외 후 지표별 중앙값을 사용한다.
- 가설·관찰·확정된 결론을 구분한다. 측정 규격이 바뀌면 같은 규격으로 전후를 재측정한다.
- 변경과 검증에 맞춰 항목을 갱신하고, 새 최적화는 별도 항목으로 추가한다.

## 2026-10-20 — 수신 버퍼 일괄 제거

### 문제 및 가설

`connection.rs`에서 프레임마다 `pending.drain(..consumed)`를 호출했다. Vec의 앞부분을 제거하면 남은 바이트가 앞으로 이동하므로, 한 버퍼에 여러 명령이 들어오는 파이프라이닝에서 반복 이동 비용이 발생할 것으로 예상했다.

가설: 처리한 바이트 수를 오프셋에 누적하고 파싱 루프 종료 후 한 번만 제거하면 반복 이동 비용을 줄일 수 있다. 이것이 실제 서버 병목인지는 측정 전에는 확정하지 않았다.

### 변경 및 검증

- 최적화 전 서버·측정 도구: `da10a37`
- 기준 측정 결과 보존: `9984e29`
- 최적화 및 회귀 테스트: `a92f6e9`
- 최적화 후 결과 보존: `fbcd0e0`
- `pending[offset..]`를 파싱하고 성공할 때마다 `offset += consumed`를 누적한다.
- 추가 수신이 필요해 루프가 끝나면 `pending.drain(..offset)`을 한 번 호출한다.
- 완성된 파이프라인 요청 뒤의 미완성 SET이 다음 수신과 정상 결합하는 회귀 테스트를 추가했다.
- 최적화 후 전체 기능 테스트 124개 통과. DB 구현은 변경하지 않았다.

### 대표 관찰 — 연결 100 / 파이프라인 256

| 지표 | 최적화 전 중앙값 | 최적화 후 중앙값 | 전 대비 변화 |
|---|---:|---:|---:|
| 처리량(req/s) | 720115.12 | 699972.00 | 약 2.8% 감소 |
| p50(ms) | 1.311 | 0.831 | 약 36.6% 감소 |
| p95(ms) | 2.991 | 2.039 | 약 31.8% 감소 |
| p99(ms) | 3.279 | 3.071 | 약 6.3% 감소 |

변화율은 `(최적화 후 - 최적화 전) / 최적화 전 × 100` 기준이다. 처리량 감소는 악화 방향, 지연 시간 감소는 개선 방향이다. 이 조건은 대표 관찰이며 전체 조건의 일괄 개선을 의미하지 않는다.

### 해석 및 다음 방안

- 이 측정 세션에서는 높은 부하 조건의 지연 시간 개선이 관찰됐지만 처리량은 소폭 감소했다. 서버 전체 성능이 개선됐다고 단정하지 않는다.
- 전후 각 한 세션, 조건별 3회 측정이므로 실행 순서와 시스템 상태에 따른 편차를 배제할 수 없다. 전후를 번갈아 재측정하여 재현성을 확인한다.
- PING은 요청이 작아 버퍼 이동 비용을 크게 드러내지 못할 수 있다. 큰 요청을 추가한다면 DB 코드를 고정하고 전후 동일 조건으로 측정한다.
- 연결 10 / 파이프라인 16의 낮은 처리량은 최적화 후에도 지속됐다. 버퍼 이동이 주요 원인이라고 확정할 근거는 없으며, 응답 전송 방식과 TCP 설정 등을 독립적인 후속 가설로 검증한다.
- 현재 판단: 기능 정합성은 확인했다. 성능 효과의 확정 및 다음 최적화 대상 선정에는 추가 실험이 필요하다.

## 2026-10-21 — TCP_NODELAY 적용

### 문제 및 가설

버퍼 일괄 제거 후에도 파이프라이닝에서 처리량이 급감했다. 같은 날 측정한 기준에서 연결 10의 처리량은 파이프라인 1일 때 약 140,056 req/s였지만 파이프라인 16에서는 약 3,621 req/s였다.

가설: 작은 응답을 명령마다 전송하는 구조에서 Nagle 알고리즘과 지연 ACK의 상호작용 등 TCP 전송 대기가 처리량을 제한할 수 있다. 이 가설을 분리해서 확인하기 위해 응답 묶음 전송이나 DB 로직은 바꾸지 않고 TCP_NODELAY만 적용한다.

- 기준 측정 기록 커밋: `d298834`
- 구현 커밋: `15510a3` — 연결 소켓에 `socket.set_nodelay(true)?` 적용

- 동일한 11개 PING 조건, 워밍업 10,000개 1회 및 본 측정 100,000개 3회. 전후 각 44회 정상 완료.

### 해소된 부분

파이프라이닝 시 급격한 처리량 저하가 이번 측정에서 크게 해소됐다. 특히 연결 10·파이프라인 16에서는 약 3,621에서 719,424 req/s로 증가했다. TCP_NODELAY가 전송 대기를 줄인다는 가설을 뒷받침하지만, 패킷 캡처 등으로 ACK 대기 구간까지 확인한 것은 아니다.

### 함께 관찰된 문제 — 고부하 지연 증가

아래는 각 지표의 3회 측정 중앙값이며 단위는 ms이다.

| 연결/파이프라인 | p50 전→후 | p95 전→후 | p99 전→후 |
|---|---:|---:|---:|
| 10/16 | 0.303 → 0.111 | 0.559 → 0.223 | 0.695 → 0.319 |
| 10/64 | 0.271 → 0.151 | 0.639 → 0.391 | 0.783 → 0.695 |
| 50/16 | 0.247 → 0.519 | 0.623 → 0.783 | 0.767 → 0.967 |
| 50/256 | 0.335 → 1.279 | 1.111 → 3.815 | 1.687 → 5.639 |
| 100/16 | 0.279 → 0.935 | 0.799 → 1.215 | 1.055 → 1.551 |
| 100/256 | 1.047 → 2.311 | 3.031 → 7.047 | 3.343 → 7.287 |

- 처리량 증가가 모든 조건의 지연 감소로 이어지지는 않았다. 파이프라인 1에서는 처리량 감소도 관찰되어 모든 작업에 대한 일괄 개선이라고 표현하지 않는다.
- 가능한 설명: 전송 대기가 줄면서 요청·패킷 처리율이 높아져 CPU·OS·클라이언트 이벤트 처리 경쟁이 증가했을 수 있다. 패킷 수나 CPU 사용률을 수집하지 않았으므로 이 원인은 미확인이다. 기존 개별 write 호출 비용이 더 드러났을 가능성도 후속 가설이다.
- redis-benchmark 7.4는 파이프라인 묶음 전송 후 첫 읽기 이벤트에서 지연을 한 번 계산하고 묶음의 응답들에 같은 값을 기록한다. 따라서 표시된 지연은 모든 개별 요청의 완료 시간이나 묶음 전체 완료 시간과 같지 않다. 첫 읽기가 늦어져도 나머지 응답이 더 빠르게 완료되면 처리량은 증가할 수 있다. [측정 구현](https://github.com/redis/redis/blob/7.4/src/redis-benchmark.c#L418-L525)
- 위 해석은 결과가 가능한 이유이며, 이번 지연 증가가 반드시 NODELAY로 인한 CPU 경쟁 때문이라고 증명한 것은 아니다.

### 판단 및 다음 방안

1. 현재 결론은 파이프라인 처리량의 큰 개선과 일부 고부하 지연 악화가 함께 관찰됐다는 것이다.
2. 다른 고부하 프로세스를 피하고 전후를 번갈아 측정하여 순서·부하 편차를 확인한다. 특히 높은 연결 조건은 측정 시간을 늘리는 것도 검토한다.
3. CPU 사용량, 패킷 수, 재전송과 패킷·ACK 타이밍을 수집해 원인 가설을 확인한다.
4. 다음 별도 실험으로 여러 응답을 모아서 전송하여 명령별 write 호출과 작은 패킷 비용을 줄일 수 있는지 검증한다. NODELAY 단독 효과와 혼합하지 않고 비교한다.

## 2026-10-21 — 응답 묶음 전송

### 문제 및 가설

TCP_NODELAY 적용으로 파이프라이닝 처리량이 크게 증가했지만, 명령마다 작은 응답을 별도로 쓰는 구조는 유지됐다. 일부 높은 연결·파이프라인 조건에서는 벤치마크 지연도 증가했다.

가설: 한 번의 수신에서 처리한 응답을 모아 전송하면 소켓 쓰기 호출과 작은 전송의 비용을 줄일 수 있다. NODELAY는 유지하고 응답 누적 방식만 추가하여 그 추가 효과를 비교한다.

### 변경 및 기능 검증

- 기준: `15510a3` (버퍼 최적화 + TCP_NODELAY)
- 구현: `e15072f` (응답 묶음 전송 및 회귀 테스트)
- 파싱 중 응답을 누적하고, 파싱 루프 종료 시 남은 응답을 전송한다.
- 4KiB 전송 기준을 넘기기 전에 기존 응답을 전송한다. 응답 하나가 기준보다 크면 추가 직후 전송한다. 이는 엄격한 메모리 상한이 아니다.
- QUIT의 OK는 앞선 응답 다음에 전송하고 연결을 종료한다.
- 파싱·인코딩 오류도 기존 누적 응답을 먼저 전송한 다음 반환한다.
- 전송 함수는 빈 버퍼를 건너뛰고 쓰기 타임아웃을 적용하며, 성공한 경우에만 버퍼를 비운다.
- 응답 크기 기준 전후의 순서 보존, 비정상 RESP 전의 응답 보존, 빈 버퍼·재사용 테스트 3개 추가. 전체 127개 테스트 통과.

### 해석 및 한계

- 파이프라이닝 조건에서는 처리량 증가와 벤치마크 지연 감소가 함께 관찰됐다. NODELAY만 적용했을 때 높은 부하에서 관찰한 지연 증가도 이 비교에서는 완화됐다.
- 비파이프라이닝 조건에서는 개선이 일관되지 않는다. 연결 100 / 파이프라인 1의 처리량은 약 130,208에서 129,032 req/s로 소폭 감소했다. 모든 조건에서 개선됐다고 표현하지 않는다.
- 높은 처리량 조건은 100,000개 요청이 약 0.01초 만에 끝났다. 측정 시간 해상도·시작 및 종료 비용·순간 부하의 영향을 크게 받을 수 있어, 정확한 배율과 절대 처리량을 확정 성능으로 제시하지 않는다.
- 현재 결론은 이 PING 파이프라이닝 실험에서 처리량과 지연의 개선 경향이 관찰됐다는 것이다. 통계적 유의성을 검증한 것은 아니다.
- 파이프라인 지연은 앞선 NODELAY 항목의 redis-benchmark 첫 읽기 이벤트 기준이라는 해석을 그대로 적용한다. 개별 요청 전체 완료 시간과 동일하지 않다.
- 큰 GET 응답, 혼합 명령 및 DB 부하의 성능은 이번 측정 범위 밖이다. 패킷 수·CPU 사용량도 수집하지 않아 개선의 내부 원인을 정량 분해하지 않았다.

## 2026-10-28 — 만료 키 정리 상한

### 문제 및 가설

[HappyBird6/mini-redis#33](https://github.com/HappyBird6/mini-redis/pull/33)에서 `purge_expired`가 만료 시각 순 인덱스(`BTreeSet<(Instant, String)>`)의 앞부분만 보도록 바뀌었다. 하지만 한 번 호출되면 만료된 키를 **전부** 지울 때까지 쓰기 락을 놓지 않았다. 만료된 키가 많이 쌓이면 그동안 들어온 `GET`이 모두 기다리게 된다.

가설: 한 번에 지우는 개수에 상한을 두면 쓰기 락을 쥐는 시간이 상한에 비례해 줄어들고, purge 중 `GET`의 최악 지연도 함께 줄어든다. 남은 키는 다음 tick에 지우거나 접근할 때 지우므로 정확성에는 영향이 없다.

Redis의 active expire cycle처럼 무작위로 키를 뽑아 확인하는 샘플링은 쓰지 않았다. Redis는 만료 키 목록이 순서 없는 해시 테이블이라 샘플링이 필요하다. 이 프로젝트는 인덱스가 만료 시각 순으로 정렬돼 있어서 앞에서부터 꺼내기만 하면 된다.

### 변경 및 기능 검증

- 테스트 선작성: `542d1b2`
  - 상한만큼만 지우기
  - 만료 시각이 이른 키부터 지우기
  - 상한 전이라도 아직 만료되지 않은 키에서 멈추기
  - 상한 0이면 아무것도 지우지 않기
  - 기존 purge 테스트는 상한 없이(`usize::MAX`) 호출하도록 변경
- 구현: `purge_expired(&self, limit: usize) -> usize`. 지운 개수가 `limit`에 닿으면 멈추고 지운 개수를 반환한다. 서버는 1초 tick마다 상한 2000으로 호출한다(아래 측정으로 결정). 상한에 닿았을 때 같은 tick 안에서 다시 돌지는 않는다.
- 전체 테스트 104개 통과(측정용 `#[ignore]` 제외).

### 측정 조건 및 근거

- [원본 CSV](benchmarks/raw/20261028-purge-limit-sweep-542d1b2.csv)
- 측정 테스트: `src/db.rs`의 `bench_purge_limit_sweep`, `bench_get_latency_during_purge`
- DB 단위 마이크로벤치마크다. 네트워크와 서버를 거치지 않는다. 앞선 항목들의 redis-benchmark 측정과는 성격이 달라 직접 비교하지 않는다.
- 측정 방식
  - 만료된 키 200,000개(키 `expired_<i>`, 값 1바이트)와 살아 있는 키 1개를 넣는다.
  - purge 스레드는 `purge_expired(limit)`를 반복 호출하고, 호출 사이에 1ms 쉰다.
  - 같은 시간에 다른 스레드가 살아 있는 키를 계속 `get`하며 한 번의 최악 지연을 기록한다.
- 상한별로 5회 측정했고, 아래 표는 각 지표의 5회 중앙값이다.
- release 빌드, rustc 1.94.0, Docker VM CPU 28개, 컨테이너별 자원 제한 없음.
- 측정 시점 구현은 `542d1b2` 위의 미커밋 변경이다.

### 판단

- 1초 tick에서 상한은 "tick마다 락을 쥐는 시간"과 "초당 정리할 수 있는 최대 개수"를 맞바꾸는 값이다. 초당 만료되는 키가 상한보다 많으면 정리가 계속 밀린다. 그래도 밀린 키는 접근할 때 지워지므로 정확성 문제는 없고 메모리만 늦게 회수된다.
- 상한 1,000과 2,000은 `get` 최악 지연이 측정 잡음 수준(약 0.5ms)으로 거의 같았다. 2,000은 정리량이 2배이고 키당 비용도 조금 낮다.
- 5,000부터는 tick마다 락을 1ms 이상 쥔다. 파이프라이닝 부하의 p50(0.05–1.2ms, 앞선 측정)과 같거나 더 큰 크기라서 꼬리 지연에 드러날 수 있다.
- 결론: 상한은 1,000–2,000 구간이 적절하다. 그중 정리량이 2배인 **2,000으로 정했다.** tick마다 락을 쥐는 시간은 약 0.35ms(가장 긴 호출 약 0.5ms)이다.

### 한계 및 다음 확인

- 결과는 DB 단위 측정이며 서버 전체 꼬리 지연에 미치는 영향은 측정하지 않았다. 정리 중 redis-benchmark p99/p99.9를 비교하려면 만료 키를 대량으로 만드는 부하가 별도로 필요하다.
- 키와 값이 작다. 값이 크면 메모리 해제 비용 때문에 키당 비용이 늘어나, 같은 상한에서도 락 시간이 길어진다.
- 한 세션에서 상한별로 5회 측정했다. 상한 사이의 차이가 1ms 미만인 구간은 잡음과 구분되지 않는다.
- 측정 루프는 호출 사이에 1ms 쉬지만, 서버는 tick 사이에 1초 쉰다. 따라서 "가장 긴 호출"은 서버의 tick당 락 시간을 나타내지만, 전체 정리 시간은 서버와 다르다.
- 초당 만료량이 상한을 계속 넘는 상황이 확인되면, 상한에 닿았을 때 같은 tick에서 락을 놓고 다시 도는 방식이나 시간 예산 방식을 별도 실험으로 검증한다.

## 2026-10-29 — 10/64 장시간 측정 편차 조사

### 문제와 확인 범위

같은 `5651d3d` 체크아웃과 5천만 PING, 연결 10개/파이프라인 64에서 첫 세션의 처리량은 124만·135만·335만 req/s, 재측정은 311만·300만·299만 req/s였다. 코드·빌드 프로필·요청 수·워밍업·Docker VM 자원(8 CPU, 약 8 GB)·컨테이너 제한·로그 설정은 같았다. 당시에는 실행 중 CPU 대기와 TCP 통계를 수집하지 않아 과거 급락 원인을 사후에 확정할 수 없다.

### 추가 실험

서버 코드를 변경하지 않고 같은 release 바이너리로 각 조건을 3회씩 측정했다. 모든 본 측정은 5천만 PING, 연결 10개/파이프라인 64이며 5초 이상이다. 서버와 생성기는 기존 두 컨테이너에서 실행했다. 진단은 양쪽 cgroup CPU 사용/제한/압력, 서버 스레드의 실행·실행 대기 시간, TCP 통계의 전후 차이를 수집했다. 초기 단계는 기존 서버를 그대로 사용했고, 나머지 단계는 100만 요청 워밍업을 수행했다. 재시작 비교는 서버를 1 worker로 재생성했다가 기본 설정으로 재생성하는 순서였다.

| 서버 worker / 생성기 thread | 처리량 중앙값(req/s) | 처리량 최소–최대 | p99 중앙값(ms) | 서버 CPU 시간 중앙값(s) |
|---|---:|---:|---:|---:|
| 기본 8 / 1, 초기 | 3,395,585.75 | 3,365,870.25–3,467,647.00 | 0.303 | 24.53 |
| 1 / 1 | 3,383,178.75 | 3,371,089.50–3,481,167.00 | 0.351 | 14.66 |
| 기본 8 / 1, 복구 후 | 3,348,289.00 | 3,342,246.00–3,355,479.50 | 0.319 | 24.58 |
| 기본 8 / 2 | 4,077,305.75 | 3,635,306.25–4,444,049.50 | 0.335 | 30.09 |

CPU 시간은 여러 코어에서 사용한 시간의 합이며 경과 시간과 다르다. 전후 스냅샷 수집 구간의 작은 오버헤드도 포함한다. `official-redis` PID 1은 Redis 서버이므로 그 스레드 통계를 부하 생성기 통계로 해석하지 않았다. 생성기 비용은 컨테이너 cgroup CPU 합계를 사용했다.

### 확인된 사실과 한계

- 추가 12회 측정에서는 과거의 124만~135만 req/s, p99 약 8 ms 상태가 재현되지 않았다.
- 모든 진단 실행에서 양쪽 컨테이너의 CPU throttling 증가와 TCP 재전송·수신 오류 증가는 0이었다. 이는 이번 실행의 관찰이며 과거 느린 구간도 같았다고 단정할 수 없다.
- 기본 설정 6회에서 서버 스레드의 실행 대기 시간 합계는 실행당 약 0.035~0.072초였다. 현재의 CPU 실행 대기가 과거의 수십 초 차이를 설명한다는 근거는 없다. Windows 호스트의 과거 부하도 기록되지 않았다.
- 서버 worker를 1개로 바꾸면 CPU 비용은 줄지만 처리량은 거의 같았다. worker 수 자체가 과거 급락의 원인이라는 가설은 이번 비교에서 뒷받침되지 않았다.
- 기본 생성기는 실행 시간 약 14.4~15.0초 동안 컨테이너 CPU를 약 14.3~14.7초 사용했다. 코어 하나에 가까운 사용량이고, 생성기 2 threads에서는 복구 후 기본값보다 처리량 중앙값이 약 21.8% 증가했다. 따라서 이 조건의 수치는 서버만의 최대 성능으로 해석하면 안 된다. 단, 생성기 2 threads 조건의 편차도 남아 있으며 이 결과가 과거 급락의 원인을 입증하지는 않는다.
- 현재 가장 정확한 결론은 **과거 급락 원인은 미확정**이라는 것이다. 일시적인 호스트/VM 부하나 실행 중 스케줄링 변화는 후보지만 당시 자료와 이번 재현만으로 특정할 수 없다. 오래 측정하는 것만으로 환경 변동이 사라지지는 않는다.
