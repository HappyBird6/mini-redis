## 실행 순서

Docker Desktop이 실행 중인 호스트 Git Bash에서 실행합니다. official-redis는 부하 생성 도구의 실행 장소이고, 측정 대상은 mini-redis입니다. Bash와 awk는 Git Bash 도구를 사용하므로 Python 설치는 필요 없습니다.

```bash
bash scripts/benchmark.sh
```

## 자동 준비 절차 및 주의 사항

스크립트가 다음을 순서대로 수행하므로 사전 빌드나 별도 서버 실행 명령은 필요 없습니다.

1. 체크아웃 커밋, 미커밋 변경, Docker 정보를 기록합니다.
2. 기존 mini-redis 서버를 중지합니다. 접속 중인 클라이언트 연결은 끊기며 메모리 DB 데이터는 사라집니다.
3. 공유 target 볼륨에 `cargo build --locked --release --bin mini-redis`로 빌드합니다. 실패하면 서버를 다시 시작하지 않고 중단합니다.
4. `BUILD_PROFILE=release`로 서버 컨테이너를 재생성하고 official-redis 도구 컨테이너를 시작합니다.
5. 실제 실행 경로와 자원·버전 정보를 기록하고, 최대 30초 동안 PONG 응답을 기다립니다.
6. 워밍업과 본 측정을 수행한 뒤 원본 및 요약을 저장합니다.

Dev Container로 mini-redis에 접속한 상태라면 중지·재생성 때 연결이 끊길 수 있으므로 호스트 터미널에서 실행하세요. 처음 실행할 때는 이미지 빌드나 다운로드가 필요할 수 있습니다. 측정 후 서버와 도구 컨테이너는 실행 상태로 남습니다.

측정할 코드는 먼저 커밋하는 것을 권장합니다. 미커밋 소스도 빌드에 포함되므로 커밋 해시만으로 그 바이너리를 재현할 수는 없습니다. 빌드와 측정 중에는 코드를 수정하거나 다른 빌드를 실행하지 마세요. 타임아웃·빌드 오류·명령 실패는 실패 세션으로 기록합니다.

## 측정 조건

| 본 측정 요청 수 (-n) | 동시 연결 (-c) | 파이프라이닝 (-P) |
|---:|---:|---:|
| 100000 | 1 | 1 |
| 100000 | 10 | 1 |
| 100000 | 50 | 1 |
| 100000 | 10 | 16 |
| 100000 | 50 | 16 |
| 100000 | 10 | 64 |
| 100000 | 10 | 256 |
| 100000 | 50 | 256 |
| 100000 | 100 | 1 |
| 100000 | 100 | 16 |
| 100000 | 100 | 256 |

총 11개 조건이며, 각 조건은 **10,000개 요청의 워밍업 1회 + 100,000개 요청의 본 측정 3회**로 총 44회 실행합니다. 실제 `-n` 값은 실행별 명령과 Conditions에 기록됩니다. 완료 횟수의 분모는 스크립트의 조건 수와 반복 수로 자동 계산합니다. 스크립트에 별도 인자는 전달하지 않습니다.

기존 로그의 워밍업은 100,000개 요청이었습니다. 이번 변경 이후 결과와 엄밀하게 비교하려면 최적화 전후 모두 같은 워밍업 요청 수로 다시 측정하세요.

100 연결 조건은 현재 최대 연결 수 100에서의 측정입니다. 다른 CLI·모니터링 연결을 닫고 실행하세요. CONFIG 조회 및 준비 확인 연결과 별개로 실제 측정 연결이 거절되지 않는지 원본과 서버 로그를 확인해야 합니다. 거절이 있으면 정상 처리량 측정으로 비교하지 않습니다.

파이프라인 256은 서버에 요청을 집중시키는 높은 부하 조건입니다. 전후 비교 시 같은 요청 수·연결 제한·DB 코드·로그 수준·Docker 자원을 유지하고, 기존 5개 조건 기록과 새로 추가한 조건을 구분하세요. 과거 요약에 없는 조건은 최적화 전 버전에서도 별도 측정해야 전후 비교할 수 있습니다.

- 원본은 실행마다 `raw/세션명-커밋.txt`로 저장합니다.
- [요약본](benchmark-summary.md)은 하나의 파일에 세션별로 자동 추가합니다.
- 워밍업은 제외하며, 정상 종료와 Summary가 확인된 3회 측정의 지표별 중앙값을 계산합니다.
- 실패하거나 중단된 세션도 요약에 표시하며, 동일 세션은 중복 추가하지 않습니다.
