## 현재 main 기준값 측정 (규격 2)

기존 `benchmark-summary.md`와 `raw/` 기록은 보존합니다. 새 측정은 현재 체크아웃의 서버를 빌드하며, 결과는 **`benchmark-baseline-summary.md`에 추가**합니다. 브랜치 이름이 main인지 강제하지 않으므로, 이 변경을 main에 반영한 뒤 실행하면 main 기준값이 됩니다. 다른 브랜치에서도 같은 규격으로 비교할 수 있습니다.

Docker Desktop이 실행 중인 호스트 Git Bash에서 실행합니다.

```bash
bash scripts/benchmark.sh
```

기본값은 대표 조건 **연결/파이프라인 10/1, 10/64, 100/256**이며, 조건마다 **100만 요청 워밍업 1회 + 5천만 요청 본 측정 3회**를 수행합니다. 총 12회이며, 느린 조건에서는 상당한 시간이 걸릴 수 있습니다. 최소 측정 시간은 5초입니다. 5천만 요청이 모든 환경에서 5초를 보장하지는 않습니다.

## 설정

| 환경변수 | 기본값 | 의미 |
|---|---|---|
| `BENCH_REQUESTS` | `50000000` | 본 측정 한 번의 요청 수 |
| `BENCH_WARMUP_REQUESTS` | `1000000` | 조건마다 한 번 실행하는 워밍업 요청 수 |
| `BENCH_RUNS` | `3` | 조건별 본 측정 횟수, 3~100 |
| `BENCH_MIN_SECONDS` | `5` | 기준값 집계에 필요한 최소 측정 시간(양의 정수 초) |
| `BENCH_CONDITIONS` | `10 1;10 64;100 256` | 세미콜론으로 구분한 `연결 수 파이프라인 수` 목록 |

요청 수·워밍업·시간·조건의 숫자는 1~2147483647 정수만 허용합니다. 빈 값, 중복 조건 및 잘못된 설정은 Docker 실행 전에 거부합니다. 스크립트에는 위치 인자를 전달하지 않습니다.

예비 측정은 한 조건부터 시작할 수 있습니다.

```bash
BENCH_CONDITIONS='10 64' BENCH_REQUESTS=1000000 bash scripts/benchmark.sh
```

요약의 측정 시간을 확인해 요청 수를 조절하세요. 예를 들어 100만 요청이 0.2초에 끝났다면 5초에 약 2500만 요청이 필요하므로 여유를 두어 늘립니다. 너무 짧은 시간의 추정은 부정확하므로 다시 확인해야 합니다.

```bash
BENCH_CONDITIONS='10 64' BENCH_REQUESTS=50000000 BENCH_RUNS=5 bash scripts/benchmark.sh
```

기존 11개 조건도 명시적으로 선택할 수 있습니다.

```bash
BENCH_CONDITIONS='1 1;10 1;50 1;10 16;50 16;10 64;10 256;50 256;100 1;100 16;100 256' bash scripts/benchmark.sh
```

## 준비와 결과 저장

스크립트는 체크아웃 커밋·미커밋 서버 변경·설정·도구 버전·Docker 자원을 기록합니다. 기존 서버를 중지하고 locked release 바이너리를 빌드한 뒤 서버를 재생성합니다. 실제 release 실행 경로와 PONG 준비 응답을 확인한 다음 워밍업과 본 측정을 수행합니다.

**실행하면 기존 연결이 끊기고 메모리 DB 데이터가 사라집니다.** Dev Container 내부 대신 호스트 터미널에서 실행하세요. 빌드 실패 시 서버를 다시 시작하지 않고 중단합니다. 측정 후 서버와 도구 컨테이너는 실행 상태로 남습니다.

- 원본: `raw/세션명-커밋.txt`에 규격 번호, 실제 명령과 설정, 실행별 종료 상태 저장
- 새 요약: `benchmark-baseline-summary.md`에 세션별 추가
- 실행별 표: 요청 수(-n), 실제 완료 요청 수, 측정 시간, 처리량, p50/p95/p99, 유효 여부
- 조건별 표: 시간·처리량·지연 중앙값, 처리량 최소–최대, 유효 측정 수

시간은 Docker 실행 전체 시간이 아닌 **redis-benchmark의 `requests completed in ... seconds`**를 사용합니다. 최소 시간 미달은 `시간 부족`으로 표시해 집계에서 제외합니다. 완료 요청 수는 -n 이상, -n+P 미만이어야 합니다. redis-benchmark 7.4는 마지막 파이프라인 응답을 끝까지 소비해 최대 P-1개 더 완료할 수 있기 때문입니다. 누락된 결과·완료 요청 수 범위 이탈·실행 번호 오류·명령 실패도 집계에 사용하지 않습니다. 조건별로 지정한 횟수 전체가 유효하고 세션이 정상 종료했을 때만 중앙값을 계산합니다. 짧은 실행 자체는 도구 오류가 아니므로 종료 코드 0이어도 기준값은 미집계일 수 있습니다.

자동으로 요청 수를 변경하거나 재시도하지 않습니다. `시간 부족`이면 해당 조건의 요청 수를 늘려 새 세션으로 측정하세요. 조건별 요청 수가 다르면 조건을 나눠 실행할 수 있습니다. 처리량 범위는 반복 간 변동을 보여주며 통계적 신뢰구간은 아닙니다.

## 기준값과 이후 비교

1. 서버 코드를 커밋한 상태에서 현재 main 기준값을 측정하고 원본·요약을 보관합니다. 미커밋 소스도 빌드되므로 커밋 해시만으로 실행 파일이 보증되지는 않습니다.
2. 이후 변경 전후에는 같은 조건별 요청 수·워밍업·반복 횟수·최소 시간·로그 수준·Docker 자원을 사용합니다. 모든 본 측정이 최소 시간을 넘는지 확인합니다.
3. 변경 전후 실행 순서를 번갈아 배치해 환경 변화 영향을 줄입니다. 측정 중 소스나 HEAD를 바꾸거나 다른 빌드를 실행하지 않습니다.
4. 과거 규격 1과 새 규격 2 결과로 개선 배율을 계산하지 않습니다. 이번 기준값은 과거 #32 개선 배율의 재검증을 뜻하지 않습니다.

100 연결 조건에서는 다른 CLI·모니터링 연결을 닫으세요. `official-redis`는 부하 생성 도구 실행 장소이고 대상은 `mini-redis`입니다. 서버 로그와 원본에서 연결 거절 여부를 확인하세요. 파이프라인 지연은 개별 요청 전체 완료 시간과 같지 않습니다.
